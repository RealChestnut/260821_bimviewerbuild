# 1. IFC의 정체와 범위

IFC(Industry Foundation Classes)는 buildingSMART International이 관리하는 개방형 국제 표준이다. 2026년 기준 현행 국제표준은 ISO 16739-1:2024이며, IFC는 건축물뿐 아니라 토목 인프라까지 포함하는 built environment의 디지털 표현을 목표로 한다. \[B1\]

- 객체의 정체성·의미: 이름, GUID, 객체 종류, 기능

- 객체의 Attribute: 위치, 형상, 재료, 색상, 열적 성능 등

- 객체 간 Relationship: 공간 포함, 조립, 연결, 타입 정의, 공정 할당 등

- 추상 정보: 비용, 성능, 일정, 작업, 자원, 책임 주체 등

- 교환 목적: 설계 → 시공 → 운영 단계에서 서로 다른 소프트웨어 사이의 정보 전달

> **중요** IFC를 “3D 형상 + 속성 몇 개”로만 보면 구조의 절반만 이해한 것이다. IFC의 강점은 Geometry와 Metadata뿐 아니라 Relationship과 Process까지 표준 객체로 표현할 수 있다는 점이다.

# 2. IFC 파일, Schema, Encoding의 차이

IFC는 데이터 모델(Schema)이고, .ifc는 그 Schema에 맞춘 데이터를 저장하는 대표적인 파일 직렬화 방식이다. 같은 IFC 데이터 모델을 여러 전자 형식으로 표현할 수 있다. \[B2\]

| **구분**                 | **확장자**  | **특징**                                      | **실무 판단**                             |
|--------------------------|-------------|-----------------------------------------------|-------------------------------------------|
| STEP Physical File (SPF) | .ifc        | 가장 널리 쓰이는 텍스트 기반 STEP 표현        | 파일 교환 기본값                          |
| ifcXML                   | .ifcXML     | XML 기반, 가독성은 높으나 파일이 더 큼        | 일반 BIM 교환에서는 비주류                |
| ifcZIP                   | .ifcZIP     | SPF/XML을 ZIP으로 압축                        | 용량 절감                                 |
| ifcOWL / Turtle          | .ttl / .rdf | RDF/시맨틱웹 표현                             | 연구·지식그래프 용도                      |
| IFC JSON                 | .json       | 후보/프로비저널 표현                          | 웹 연동 가능성 있으나 일반 교환 주류 아님 |
| HDF / SQLite             | 다양        | 대형 모델의 인덱스 접근을 위한 후보/실험 계열 | 일반 납품형식 아님                        |

ISO-10303-21;  
HEADER;  
...  
FILE_SCHEMA(('IFC4'));  
ENDSEC;  
DATA;  
\#1=IFCPROJECT(...);  
...

따라서 현장에서 “IFC 파일”이라고 하면 대개 STEP Physical File 형식의 .ifc를 의미한다. buildingSMART도 파일 기반 Import/Export에서 가장 넓은 호환성을 위해 SPF를 권장한다. \[B2\]

# 3. IFC Schema 버전 체계

IFC2x3, IFC4, IFC4.3은 “IFC Type”이 아니라 IFC Schema 버전이다. Schema가 바뀌면 사용할 수 있는 Entity, Attribute, 관계, Geometry 표현과 의미 범위가 바뀔 수 있다. \[B3\]

| **버전**      | **공식 명칭** | **상태(2026-08)** | **ISO / 공개시점**           | **의미**                      |
|---------------|---------------|-------------------|------------------------------|-------------------------------|
| IFC2x3 TC1    | 2.3.0.1       | Official          | ISO/PAS 16739:2005 / 2007-07 | 오래됐지만 매우 넓은 호환성   |
| IFC4 ADD2 TC1 | 4.0.2.1       | Official          | ISO 16739-1:2018 / 2017-10   | IFC4 계열의 공식 안정판       |
| IFC4.1        | 4.1.0.0       | Withdrawn         | 2018-06                      | 중간 개발 릴리스              |
| IFC4.2        | 4.2.0.0       | Withdrawn         | 2019-04                      | 중간 개발 릴리스              |
| IFC4.3 ADD2   | 4.3.2.0       | Official          | ISO 16739-1:2024 / 2024-04   | 도로·철도·교량 등 인프라 확대 |
| IFC4.4        | 4.4.x dev     | 개발 중           | \-                           | 4.3 확장 및 수정              |
| IFC5          | 5.0 dev       | 개발 중           | \-                           | 차세대 재구성                 |

buildingSMART의 버전 표기는 Major.Minor.Addendum.Corrigendum 구조다. Major는 호환성을 깨뜨릴 수 있는 범위 변경, Minor는 기능 확장, Addendum은 기존 기능 개선, Corrigendum은 주로 문서·정정에 해당한다. \[B3\]

# 4. IFC2x3 / IFC4 / IFC4.3 비교

| **항목**           | **IFC2x3**                  | **IFC4**                                 | **IFC4.3**                                |
|--------------------|-----------------------------|------------------------------------------|-------------------------------------------|
| 건축 BIM           | 강함                        | 강함·구조 개선                           | 강함                                      |
| 구조/MEP           | 지원                        | 개선                                     | 지원                                      |
| Property/Type 체계 | 기본                        | 개선·정교화                              | 확장                                      |
| Geometry 표현      | 구형 중심                   | 개선                                     | 인프라·선형 포함 개선                     |
| 지리참조           | 제한적                      | 개선                                     | 인프라 수준 강화                          |
| 공정/Task          | 가능                        | IfcTask/IfcTaskTime 활용이 더 자연스러움 | 동일 + 인프라                             |
| 도로/철도/교량     | Proxy·범용 객체 의존이 많음 | 부분적                                   | IfcRoad/IfcRailway/IfcBridge 등 본격 지원 |
| Alignment          | 약함                        | 초기/제한                                | IfcAlignment 및 선형 위치 지원 강화       |
| 실무 호환성        | 매우 높음                   | 높음                                     | 확대 중, 구현차 확인 필요                 |

IFC4.3의 핵심은 건물 중심 BIM에서 시설·인프라 BIM으로 범위를 넓힌 것이다. Schema에 새로운 인프라 Entity와 선형 위치 개념이 포함됐다. \[B4\]

> **실무 원칙** 최신 버전이 무조건 최선은 아니다. IFC4.3 Schema가 표현할 수 있는 정보가 가장 넓어도, 실제 Exporter·Viewer가 그 Entity와 관계를 얼마나 구현했는지가 별개다. 따라서 “IFC4.3 지원”이라는 표기만으로 완전한 호환성을 가정하면 안 된다.

# 5. Entity와 상속 구조

Entity는 IFC에서 “무엇인가”를 정의하는 Class에 해당한다. 예를 들어 기둥은 IfcColumn, 보는 IfcBeam, 공정 작업은 IfcTask다. Entity는 상속구조를 가지므로 하위 Entity는 상위 Entity의 Attribute와 관계 개념을 물려받는다.

IfcRoot  
└─ IfcObjectDefinition  
└─ IfcObject  
└─ IfcProduct  
└─ IfcElement  
└─ IfcBuiltElement / IfcBuildingElement 계열  
└─ IfcColumn, IfcBeam, IfcSlab ...

| **Entity 영역**   | **대표 Entity**                                           | **역할**                      |
|-------------------|-----------------------------------------------------------|-------------------------------|
| Project / Spatial | IfcProject, IfcSite, IfcBuilding, IfcBuildingStorey       | 프로젝트·공간 구조            |
| Building Element  | IfcColumn, IfcBeam, IfcWall, IfcSlab, IfcPile, IfcFooting | 물리 부재                     |
| Assembly          | IfcElementAssembly                                        | 여러 Element로 구성된 조립체  |
| Infrastructure    | IfcRoad, IfcRailway, IfcBridge, IfcAlignment              | 인프라 시설/선형(IFC4.3 중심) |
| Process           | IfcTask, IfcWorkSchedule                                  | 공정 작업 및 일정             |
| Relationship      | IfcRelAggregates, IfcRelAssignsToProcess, IfcRelSequence  | 객체 간 관계                  |
| Property          | IfcPropertySet, IfcPropertySingleValue 등                 | 추가 의미정보                 |

# 6. IFC에서 “Type”이라는 말의 여러 의미

| **용어**       | **예**                  | **의미**                                  |
|----------------|-------------------------|-------------------------------------------|
| Schema Version | IFC4.3                  | IFC 데이터 구조의 세대/버전               |
| Entity Type    | IfcColumn               | 객체 Class                                |
| PredefinedType | USERDEFINED 등          | 특정 Entity 내부의 세부 분류              |
| Type Object    | IfcColumnType           | 여러 Occurrence가 공유하는 공통 타입 정의 |
| Occurrence     | IfcColumn 개별 인스턴스 | 실제 모델 안의 개별 부재                  |

IfcColumnType "RC Column 600x600"  
├─ IfcColumn \#1  
├─ IfcColumn \#2  
└─ IfcColumn \#3

따라서 “IFC Type”이라는 표현은 문맥 없이 쓰면 위험하다. Schema 버전을 말하는지, Entity를 말하는지, PredefinedType이나 Type Object를 말하는지 구분해야 한다.

# 7. Entity Attribute

Entity Attribute는 Schema가 정의하는 구조적 필드다. Exporter는 값 채우기 여부에는 영향을 줄 수 있지만 Attribute 이름 자체를 임의로 새로 정의할 수는 없다.

| **Attribute**    | **정의 위치**    | **의미**                                | **내부 Viewer 중요도** |
|------------------|------------------|-----------------------------------------|------------------------|
| GlobalId         | IfcRoot          | 전 세계적으로 고유해야 하는 IFC 식별자  | 매우 높음              |
| OwnerHistory     | IfcRoot          | 소유/작성/변경 이력(일부 버전에서 선택) | 낮음                   |
| Name             | IfcRoot          | 객체 이름                               | 높음                   |
| Description      | IfcRoot          | 설명                                    | 중간                   |
| ObjectPlacement  | IfcProduct       | 객체 위치 및 로컬 좌표계                | 매우 높음              |
| Representation   | IfcProduct       | 형상/표현                               | 매우 높음              |
| ObjectType / Tag | 하위 Entity 계열 | 세부 식별·분류                          | 중간~높음              |
| PredefinedType   | 해당 Entity      | Schema가 정의한 세부 유형               | 높음                   |

IfcRoot는 GlobalId, OwnerHistory, Name, Description을 정의한다. IfcProduct는 ObjectPlacement와 Representation을 통해 공간 배치와 Geometry를 연결한다. \[B5\]\[B6\]

# 8. Geometry와 Placement

IFC는 “어디에 있는가”와 “어떻게 생겼는가”를 분리한다. ObjectPlacement가 객체 좌표계를 정의하고 Representation이 그 좌표계 안의 형상을 정의한다. \[B6\]\[B7\]

IfcProduct  
├─ ObjectPlacement → 위치 / 회전 / 좌표계  
└─ Representation → Shape / Geometry

| **Placement 방식** | **설명**                           | **주의**                 |
|--------------------|------------------------------------|--------------------------|
| Absolute / Local   | 프로젝트/월드 기준 또는 로컬 기준  | 실제 월드 좌표 계산 필요 |
| Relative           | 상위 객체 Placement 기준 상대 위치 | 계층 누적 변환 필요      |
| Grid Placement     | Grid 축 기준                       | 특수 설계 모델           |
| Linear Placement   | 선형/Alignment 기준 거리와 Offset  | IFC4.3 인프라에서 중요   |

Web Viewer 내부 표준에는 단순 XYZ만 저장하기보다 최종 4×4 Transform Matrix, 원본 좌표계, 단위, 원점 오프셋, 상위 Placement 추적정보를 함께 보존하는 것이 안전하다.

# 9. 공간 구조와 Assembly

IFC는 건물/시설의 공간 계층과 물리 부재의 조립 관계를 Relationship으로 표현한다. 공간 계층을 단순 Property 문자열로만 표현하는 구조와 다르다.

IfcProject  
└─ IfcSite  
└─ IfcBuilding / IfcFacility  
└─ IfcBuildingStorey / FacilityPart  
└─ Elements

조립체는 IfcElementAssembly와 IfcRelAggregates 등을 이용해 표현할 수 있다. IFC4.3 문서는 Assembly가 여러 Element로 구성될 수 있고 Assembly 안에 또 Assembly를 둘 수 있는 중첩 구조를 허용한다. \[B8\]

IfcElementAssembly  
├─ IfcBeam  
├─ IfcPlate  
└─ IfcElementAssembly  
└─ ...

> **Granularity 문제** IFC가 Assembly 관계를 표현할 수 있다고 해서 외부 설계사가 원하는 공정 단위로 모델을 쪼개 준다는 뜻은 아니다. 원본 모델이 공정 단위보다 너무 크게 합쳐져 있으면 Split, 너무 잘게 나뉘어 있으면 Group이 필요하다. 이는 Schema 문제가 아니라 모델링 Granularity 문제다.

# 10. Property와 Property Set

Property는 Entity의 고정 Attribute 외에 객체에 추가 의미정보를 붙이는 구조다. PropertySet은 여러 Property를 묶는 컨테이너다. 표준 PropertySet과 사용자 정의 PropertySet을 구분해야 한다. \[B9\]

| **구분**                 | **누가 정의**          | **예**                    | **프로그램별 차이**              |
|--------------------------|------------------------|---------------------------|----------------------------------|
| Entity Attribute         | IFC Schema             | GlobalId, ObjectPlacement | 구조 고정                        |
| 표준 Property Set        | buildingSMART IFC 표준 | Pset_ColumnCommon         | Exporter가 포함하지 않을 수 있음 |
| 사용자 정의 Property Set | 회사/프로젝트/Exporter | Company_4D, ProjectData   | 자유롭게 다를 수 있음            |

IFC4.3 문서는 표준 PropertySet에는 Pset\_ 접두어를 사용하며, IFC 표준에 정의되지 않은 사용자 정의 PropertySet은 Pset\_ 접두어를 사용하지 말라고 명시한다. \[B9\]

# 12. Relationship

IFC의 핵심은 객체 간 관계를 별도의 Entity로 표현한다는 점이다. 단순히 각 객체의 Property에 ParentId나 TaskId를 문자열로 적는 것과 다르다.

| **Relationship Entity**           | **역할**                   | **예**                    |
|-----------------------------------|----------------------------|---------------------------|
| IfcRelAggregates                  | 조립/분해 계층             | Assembly ↔ Part           |
| IfcRelContainedInSpatialStructure | 공간 포함                  | Storey ↔ Column           |
| IfcRelDefinesByProperties         | PropertySet 연결           | Element ↔ Pset            |
| IfcRelDefinesByType               | Occurrence와 Type 연결     | IfcColumn ↔ IfcColumnType |
| IfcRelAssignsToProcess            | 객체를 공정/Process에 할당 | Task ↔ Elements           |
| IfcRelSequence                    | Process 선후행 관계        | T001 → T002               |

IfcRelAssignsToProcess는 하나 이상의 Object를 단일 Process에 연결할 수 있으며, 설치·마감·운반·제거 같은 작업 의미도 표현할 수 있다. \[B11\] IfcRelSequence는 predecessor와 successor의 순서를 표현하고 START_START, FINISH_START 등과 같은 SequenceType을 지원한다. \[B12\]

# 13. 공정·4D 데이터 구조

IFC는 Geometry만 다루는 포맷이 아니다. 일정·작업을 Process Entity로 표현할 수 있다. 특히 IFC4 계열에서는 IfcTask, IfcTaskTime, IfcWorkSchedule, IfcRelSequence, IfcRelAssignsToProcess를 활용해 4D 데이터 모델을 구성할 수 있다.

IfcWorkSchedule  
├─ IfcTask T001  
│ └─ IfcTaskTime  
├─ IfcTask T002  
└─ ...  
  
IfcRelSequence: T001 → T002  
IfcRelAssignsToProcess: T001 ↔ Column01, Column02

# 14. MVD와 실제 소프트웨어 호환성

IFC Schema는 매우 크기 때문에 모든 프로그램이 모든 Entity와 관계를 구현할 필요는 없다. 특정 업무에 필요한 IFC Schema의 부분집합과 추가 제약을 Model View Definition(MVD)이라고 한다. IFC4.3 용어 정의에서는 MVD를 “특정 데이터 요구사항을 만족하는 Schema의 subset”으로 정의한다. \[B14\]

IFC 전체 Schema  
↓  
특정 교환 요구사항  
↓  
MVD / Exchange  
↓  
Exporter / Importer 실제 구현

따라서 “프로그램 A와 B가 둘 다 IFC4를 지원한다”는 사실만으로 완전 호환을 보장할 수 없다. 어떤 Entity, Property, Geometry Representation, Relationship, MVD/Exchange를 구현했는지 확인해야 한다.

# 15. Export 프로그램에 따라 IFC가 달라지는 이유

IFC 표준 자체는 벤더 중립이지만, 최종 IFC 파일에 어떤 정보가 들어갈지는 원본 프로그램, Exporter, Export 설정, Target Schema, 사용자 Mapping에 따라 달라진다. \[B1\]

원본 모델 데이터  
+ IFC Exporter  
+ Export 설정  
+ Target IFC Schema  
+ 사용자 Property/Class Mapping  
= 최종 IFC 파일

| **구조**                | **표준에서 고정되는가** | **Exporter 영향**              | **예**                        |
|-------------------------|-------------------------|--------------------------------|-------------------------------|
| Schema 규칙             | 예                      | 선택한 버전만 영향             | IFC2x3 / IFC4 / IFC4.3        |
| Entity 정의             | 예                      | 어떤 Entity로 Mapping할지 영향 | IfcColumn / IfcBeam           |
| Entity Attribute 이름   | 예                      | 값 생성/누락에 영향            | GlobalId, ObjectPlacement     |
| 표준 Pset 정의          | 예                      | 포함 여부·값에 영향            | Pset_ColumnCommon             |
| 사용자 Pset             | 아니오                  | 매우 큼                        | Company_4D                    |
| Property 이름/값        | 아니오(사용자 영역)     | 매우 큼                        | TaskId, Zone                  |
| Geometry Representation | Schema 범위 내          | 매우 큼                        | BRep / Tessellation           |
| Granularity             | 아니오                  | 원본 모델·선택방식 영향        | Assembly 하나 vs Part 여러 개 |

따라서 같은 기둥을 Revit, Tekla, Archicad, Navisworks+Plugin에서 IFC로 내보내도 Entity는 IfcColumn으로 같을 수 있지만 Custom PropertySet과 값 구성은 달라질 수 있다. 심지어 같은 프로그램도 Export 설정에 따라 다르게 나온다.

# 16. Navisworks 생태계에서의 IFC

> **가장 중요한 전제** Navisworks 자체에는 2026년 현재도 Built-in IFC Export가 없다. Autodesk 공식 지원 문서는 IFC Export가 서드파티 플러그인(Codemill, iConstruct 등)의 기능이라고 명시한다. [N1]

Navisworks  
┌──────┼────────┐

└──────┼────────┘

IFC Exporter  
↓

↓  
IFC

## 16.4 Codemill IFC Exporter의 Mapping 구조

현재 Codemill 문서는 두 가지 Export 방식을 설명한다. \[N3\]

| **방식**            | **동작**                                                                                     | **표준화 관점**                                                                 |
|---------------------|----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| Mapping 없이 Export | 선택한 Model Item 수만큼 IFC Element 생성. 문서상 기본 Entity는 IfcEquipmentElement라고 설명 | 빠르지만 의미 분류가 약함. IFC4/4.3에서의 fallback Entity는 실제 샘플 검증 권장 |
| Object Mapping 사용 | Selection/Search Set별로 사용할 IfcElement 지정                                              | Class 표준화에 유리                                                             |
| Property Mapping    | Navisworks Property → IfcPropertySet/IfcQuantitySet                                          | 내부 필수 속성 표준화 가능                                                      |
| TimeLiner Export    | 구버전은 Property 중심, 2027/5.0은 IfcTask 생성 옵션                                         | 4D 표준화 가능성 증가                                                           |

> **Codemill 문서 검증 포인트** 현재 도움말은 IFC2x3/IFC4/IFC4x3을 생성한다고 하면서 Mapping 없이 모든 Entity를 IfcEquipmentElement로 표시한다고 설명한다. 이 Class의 Schema 세대별 존재/대체 관계 때문에 IFC4/4.3 실제 출력 fallback Class는 반드시 샘플 Export로 확인하는 것이 좋다.

## 16.5 Navisworks Property와 IFC Property의 관계

| **Navisworks 측**           | **IFC 측**                           | **주의**                                                   |
|-----------------------------|--------------------------------------|------------------------------------------------------------|
| 원본 Model Property         | Property/Pset 후보                   | 원본 CAD Property는 Navisworks에서 읽기 전용인 경우가 많음 |
| User Data / Custom Property | Custom IfcPropertySet 후보           | 프로젝트 표준 속성 추가에 유용                             |
| Property Category           | IfcPropertySet.Name으로 Mapping 가능 | 명칭 규칙을 별도 정의하는 것이 좋음                        |
| Property Name/Value         | IfcProperty.Name / Value             | Exporter의 Type 변환 규칙 검증 필요                        |
| Selection/Search Set        | Entity Mapping 기준                  | Property가 아니라 분류/선택 구조                           |
| TimeLiner                   | Property 또는 IfcTask                | 플러그인 버전별 차이                                       |

## 16.6 Selection Granularity와 IFC Element 개수

Codemill 도움말은 Export 시작 시 선택된 Model Item 단위를 기준으로 IFC Element 개수를 결정한다고 설명한다. 개별 Item 10개를 선택하면 10개 IFC Element가 되고, 상위 Group 하나만 선택하면 하나의 IFC Element가 될 수 있다. \[N3\]

Navisworks Selection  
├─ 개별 10개 Item 선택 → IFC Element 10개  
└─ 상위 Group 1개 선택 → IFC Element 1개

따라서 Navisworks를 “다양한 입력 포맷을 IFC로 표준화하는 허브”로 쓰려면 Search/Selection Set 설계가 공정 Granularity와 직접 연결된다.

# 17. 첨부 IFC 예제 해석

대화에 첨부된 예제 IFC는 Header에서 FILE_SCHEMA(('IFC2X3'))를 선언하므로 IFC2x3 Schema를 사용한다. 또한 IfcBuildingElementProxy 객체에 별도의 사용자 PropertySet을 연결해 4D 정보를 넣고 있다.

| TaskId            | 공정 ID             | 사용자 정의         |
| Order             | 공정 순서           | 사용자 정의         |

# 18. Web BIM/4D Viewer 내부 표준화 관점

외부 IFC를 받는 시스템에서는 특정 Property 이름을 전제로 설계하면 쉽게 깨진다. 상대적으로 안정적인 Schema/Entity/Placement/Geometry와 불안정한 Custom Property 영역을 분리해 처리해야 한다.

| **정보**                | **안정성** | **내부 처리 원칙**                              |
|-------------------------|------------|-------------------------------------------------|
| Schema Version          | 매우 높음  | Header에서 판별                                 |
| GlobalId                | 높음       | 원본 추적 ID로 보존                             |
| Entity Type             | 높음       | Schema Adapter로 공통 Class에 Mapping           |
| ObjectPlacement         | 높음       | 최종 World Transform 계산 + 원본 관계 보존      |
| Representation/Geometry | 높음       | Rendering Asset로 파생                          |
| Spatial Structure       | 중~높음    | 가능하면 보존                                   |
| Assembly 관계           | 중간       | 원본 관계 보존 + 필요 시 내부 Group/Split       |
| 표준 Pset               | 중간       | 있으면 활용, 없다고 실패 처리 금지              |
| Custom Property         | 낮음       | Exporter별 Mapping 규칙 적용                    |
| Task/4D                 | 낮음~중간  | IfcTask 존재 시 활용, 없으면 외부 Schedule 사용 |
| 공정 Granularity        | 낮음       | 모델과 공정 단위 비교 후 Group/Split            |

# 19. 권장 내부 데이터 모델과 변환 흐름

내부 표준화를 “모든 입력을 무조건 새 IFC로 다시 만드는 작업”으로 정의할 필요는 없다. 더 안전한 정의는 어떤 IFC 버전과 Exporter에서 온 파일이든 동일한 내부 의미 구조로 흡수하는 것이다.

외부 IFC (2x3 / 4 / 4.3)  
↓  
Schema 판별  
↓  
Entity / Attribute 추출  
↓  
Geometry / Placement 추출  
↓  
Relationship 추출  
↓  
Pset / Qto 전체 수집  
↓  
Exporter별 Property Mapping  
↓  
내부 Element Registry + Geometry Asset + Hierarchy  
↓  
Schedule / Task-Element Mapping  
↓  
Web Rendering Asset (Fragments .frag — ADR-0001로 확정)  
↓  
4D Viewer

## 19.1 최소 내부 Element Registry

| **필드**                  | **역할**                | **IFC 원천**                          |
|---------------------------|-------------------------|---------------------------------------|
| element_id                | 내부 고유 ID            | 내부 생성                             |
| source_file_id            | 원본 파일 식별          | 수령/파일관리                         |
| source_element_id         | 원본 IFC GUID           | GlobalId                              |
| entity_type               | 부재 종류               | IfcColumn 등                          |
| name                      | 표시명                  | Name / Tag Mapping                    |
| parent_id                 | 내부 Assembly/Hierarchy | RelAggregates/Containment + 내부 보정 |
| geometry_asset_id         | Rendering Geometry 참조 | Representation 파생                   |
| transform                 | World Transform         | ObjectPlacement 누적                  |
| bbox                      | 공간 인덱싱             | Geometry에서 계산                     |
| source_properties         | 원본 Pset/Qto 보존      | 전체 Property                         |
| split_from / grouped_from | 분해/병합 계보          | 내부 전처리 이력                      |
| version                   | 내부 변환 버전          | 내부 생성                             |

## 19.2 공정정보는 별도 계층으로 분리

| **데이터 영역**      | **핵심 ID**                      | **내용**                                       |
|----------------------|----------------------------------|------------------------------------------------|
| Element Registry     | element_id                       | 무엇이 어디에 있는가                           |
| Geometry Asset       | geometry_asset_id                | 실제 Web 표시 형상                             |
| Schedule             | task_id                          | 언제 무엇을 하는가                             |
| Task-Element Mapping | task_id + element_id             | 어떤 작업이 어떤 부재를 표시/제거/이동시키는가 |
| Source Trace         | source_file_id/source_element_id | 원본 추적                                      |

이 구조는 동일 Geometry를 여러 Element가 Pose만 다르게 참조하는 Instancing, Assembly 단위 동시 표시, 공정별 SHOW/HIDE/REMOVE 같은 액션을 구현하기 쉽다.

> **결정 반영 (2026-08-21)** 본 절의 `SHOW/HIDE/REMOVE`와 17절 예제의 `appear/temporary`는 외부 사례를 서술한 표기다. 내부 어휘는 `docs/adr/0002-4d-operation-vocabulary.md`에서 `TaskOperation`(CONSTRUCT/DEMOLISH/TEMPORARY/MODIFY)과 `ElementDisplayState`(HIDDEN/IN_PROGRESS/PRESENT)로 확정했다. 구현은 ADR-0002를 따른다. 또한 19절 흐름의 Web Rendering Asset 포맷은 `docs/adr/0001-web-rendering-asset-format.md`에서 Fragments(.frag)로 확정했다.

# 21. 용어집

|------------------------|-------------------------------------------------------------------------|
| IFC                    | Industry Foundation Classes. built environment BIM 데이터의 개방형 표준 |

| Pset                   | Property Set. 표준 Pset은 Pset\_ 접두어                                 |
| Qto                    | Quantity Set. 표준 수량 세트는 Qto\_ 접두어                             |
| Relationship           | IfcRel... 계열로 표현하는 객체 간 관계                                  |
| GlobalId               | IfcRoot에서 제공하는 IFC GUID                                           |
| Placement              | 객체의 위치/로컬 좌표계                                                 |
| Representation         | 객체의 Geometry/표현                                                    |
| Occurrence             | 모델 안의 개별 객체 인스턴스                                            |
| Type Object            | 여러 Occurrence가 공유하는 타입 정의                                    |
| PredefinedType         | Entity 내부 세부 분류 Enum                                              |
| MVD                    | 특정 교환 요구를 위한 IFC Schema subset + 제약                          |
| Exporter               | 원본 프로그램 데이터와 IFC Schema를 Mapping하여 IFC를 생성하는 변환기   |
| Granularity            | 객체가 공정/분류에 필요한 수준으로 얼마나 분해되어 있는지               |
| IfcTask                | IFC Process 작업 Entity                                                 |
| IfcTaskTime            | Task의 계획/실제 시간정보                                               |
| IfcRelAssignsToProcess | 객체를 Process/Task에 연결하는 관계                                     |
| IfcRelSequence         | Process 간 선후행 관계                                                  |
